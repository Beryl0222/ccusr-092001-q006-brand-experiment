# 老字号新业务试验 · 宠物摄影后端

传统照相馆试水宠物摄影后，套餐试验、摄影师转岗认证、动物安全告知与照片传播授权
不再混在普通订单备注里。本服务是管理新业务「小范围试验 → 正式推广」全过程的独立后端：

- 门店提交**套餐试验方案与容量**，试验按版本迭代，正式推广即版本切换；
- 员工完成**宠物摄影能力认证**后才能排班，支持跨店调班并留痕；
- 顾客对**现场拍摄 / 成片交付 / 门店展示 / 公开传播**分别授权、分别撤回；
- 撤权对**未发布内容立即阻断**，对**已发布内容按渠道生成下架任务并持续追踪**；
- 宠物应激、现场事故进入**独立处置链**（接收 → 认领 → 复核 → 闭环），重复报送自动合并；
- 管理者可**跨店、跨试验版本比较真实转化与风险**；门店只能接触本门店数据；
- **重启可恢复**：卡在「处理中」的下架任务重新入队，未闭环事件继续推进。

`domain.json` 是门店交换数据时的基础词表，所有阶段、授权范围、事件等级均以它为准。

## 运行

```bash
python3 service.py --check          # 校验 domain.json 词表
python3 service.py --port 8000      # 启动（默认库 data/petphoto.db）
# 环境变量：PET_DB（数据库路径）、ADMIN_TOKEN（管理者令牌，默认 dev-admin-token）
```

健康检查：`GET /health` → `{"status":"ok","service":"heritage-brand-experiment"}`。

所有业务接口在 `/api` 下，使用 `Authorization: Bearer <token>`：

- 管理者令牌（`ADMIN_TOKEN`）：跨店对比、认证、复核、全量追踪；
- 门店令牌：创建门店时一次性返回，只能访问本门店数据（跨店访问返回 404，不泄露存在性）。

## 关键业务规则

### 套餐试验与版本

试验阶段取自词表：`提案 → 小范围开放 → 扩大验证 → 正式经营`，任何阶段可转「暂停」，
暂停后可恢复到相应阶段，不能跳级（如「小范围开放」不能直接到「正式经营」）。

- 同名套餐每次提交方案产生一个版本：试验期内迭代小版本（1.0、1.1…）；
- 进入「正式经营」时生成下一主版本（2.0，状态「生效」），历史试验版本全部「归档」并停止接单；
- 只有「小范围开放 / 扩大验证 / 正式经营」阶段可接单，「提案」「暂停」不接单；
- 订单记录下单时的套餐名、版本与阶段快照，保证事后对比归属准确。

### 容量

按门店按天设置容量（`PUT /api/capacity`）；预约计数、满额拒绝（409）；取消订单释放名额。

### 认证与排班

- 员工注册后默认未认证，管理者通过认证后才能排班，未认证排班返回 403；
- 认证是员工个人资质，随人走：排到非归属门店即为**跨店调班**（`cross_store=true`，
  记录 `home_store_id` 与服务门店）；
- 同一员工同一天同一时段只能有一条有效排班；
- 只有服务门店可以取消该工位排班。

### 分项授权与撤回

四项授权相互独立，撤回一项不影响其他项；可重新授权（另起新记录，撤回历史保留）。

| 撤回的授权 | 影响 |
|---|---|
| 现场拍摄 | 尚未开拍的订单不能开拍（已拍摄的不追回） |
| 成片交付 | 已拍未交的订单停止交付 |
| 门店展示 | 店内电子屏等「店内」受众发布逐渠道生成下架任务 |
| 公开传播 | 小红书/抖音等「公开」渠道逐渠道生成下架任务；未发布成片标记为阻断，禁止再发 |

下架任务由后台线程推进：成功则发布置「已下架」、任务「已完成」；外部渠道暂时失败时
任务回到「待处理」并记录 `attempts` 与 `last_error`，稍后自动重试。投诉等非撤权原因
也可通过 `POST /api/publications/{id}/takedown` 手动发起。

### 现场事件处置链

事件等级取自词表：`一般记录 / 服务中断 / 安全关注 / 严重事故`（附处置时限 SLA 与超时标记）。
链路：`待响应 → 处理中（门店认领）→ 待复核（门店提交）→ 已闭环（管理者复核通过）`；
复核驳回则退回「处理中」。门店不能自行闭环。

重复报送两种识别方式：
- 显式 `client_ref`（门店工单号）：永久合并到同一事件；
- 未提供时：30 分钟内同店、同订单、同等级、同标题的未闭环事件按内容指纹合并；
合并会在处置日志中留痕（「重复报送已合并」）。

### 重启恢复

服务启动时自动执行恢复：状态为「处理中」的下架任务回到「待处理」；「处理中」的
事件退回「待响应」并记录「重启恢复」日志。任务与事件全部持久化，无需人工干预。

## 接口一览

管理者（`/api/admin/...`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/admin/stores` | 创建门店，返回一次性门店令牌 |
| GET | `/admin/stores` | 门店目录 |
| POST | `/admin/staff/{id}/certify` | 员工能力认证 |
| GET | `/admin/packages` | 全部门店套餐版本 |
| GET | `/admin/comparison` | 各版本真实转化与风险对比 |
| GET | `/admin/incidents?include_closed=0` | 全部事件 |
| POST | `/admin/incidents/{id}/review` | 复核（`approve`/`note`） |
| GET | `/admin/takedowns` | 全量下架追踪 |
| GET | `/admin/schedules?cross_store=1` | 排班 / 仅跨店调班 |

门店：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST/GET | `/staff` | 注册 / 查看本门店员工 |
| POST/GET | `/packages` | 提交试验方案 / 版本列表 |
| POST | `/packages/{id}/transition` | 阶段流转（`stage`） |
| PUT/GET | `/capacity` | 设置 / 查询当日容量 |
| POST/GET | `/orders` | 预约 / 订单列表 |
| POST | `/orders/{id}/cancel|shoot|deliver` | 取消 / 开拍 / 交付 |
| GET/POST | `/orders/{id}/consents` | 授权列表 / 授予（`scope`） |
| POST | `/orders/{id}/consents/revoke` | 撤回（`scope`,`reason`） |
| POST | `/assets` | 登记成片（`order_id`） |
| POST | `/assets/{id}/publish` | 发布（`channel`,`audience=公开/店内`） |
| GET | `/publications` | 发布与下架状态 |
| POST | `/publications/{id}/takedown` | 手动要求下架 |
| GET | `/takedowns` | 本门店下架任务追踪 |
| POST/GET | `/incidents` | 报送（支持 `client_ref` 幂等）/ 列表 |
| POST | `/incidents/{id}/ack|resolve` | 认领 / 提交复核 |
| POST/GET | `/schedules` | 排班 / 排班表（支持 `day`） |
| POST | `/schedules/{id}/cancel` | 取消排班 |

## 验证

```bash
python3 -m unittest -v        # 31 个测试：领域规则 26 + 健康检查 1 + HTTP 端到端 4
```

测试覆盖：四类授权撤回的阻断与放行边界、撤权后逐渠道下架与失败重试、重启恢复、
事故重复报送合并与处置链驳回/闭环、跨店调班冲突与门店隔离、套餐版本切换与归档、
容量满额与取消释放、管理者版本对比口径（取消单不计入有效转化）。

## 数据存储

SQLite（WAL 模式，外键开启），表结构见 `app/db.py`：门店、员工、套餐版本、容量、
订单、漏斗事件、授权（历史行）、成片、发布（按渠道）、下架任务、事件与处置日志、排班。
写入在核心层串行化，适配多线程 HTTP 服务。
